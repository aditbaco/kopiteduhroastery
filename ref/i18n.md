# Internationalization

Bilingual Indonesian / English, hand-rolled — **no i18n library**. Everything lives in
`src/dictionaries/`.

## Locale routing

```ts
LANGS = ['id', 'en'] as const
type Lang = 'id' | 'en'
DEFAULT_LANG = 'id'
```

The locale is the first path segment (`src/app/[lang]/`). `src/app/[lang]/layout.tsx` guards
it with `isLang(value)` and calls `notFound()` for anything else, so `/fr/koleksi` is a real
404 rather than a crash. `generateStaticParams` over `LANGS` prerenders both locales.

`next.config.ts` redirects `/` → `/id` with `permanent: false`. There is no `i18n` config
block and no Accept-Language negotiation — the 307 leaves room to add it later.

The language toggle in the header rewrites the current path:
`pathname.replace(/^\/(id|en)/, '/' + otherLang)`.

`<html lang>` is set per-locale by an inline script in the storefront layout rather than on
the root `<html>` element — the root layout must stay free of dynamic APIs to keep the
storefront statically rendered. See
[architecture.md](architecture.md#rendering-strategy).

## Dictionaries

`src/dictionaries/id.ts` is the **source of truth**, written `as const`. `en.ts` is typed
against it:

```ts
type Dictionary = Widen<typeof id>   // recursive: literal string types → string
const en: Dictionary = { ... }
```

`Widen<T>` preserves the exact key structure while relaxing each literal to `string`. The
effect: a missing or misspelled key in `en.ts` is a **compile error**, but English isn't
forced to repeat Indonesian literals.

`getDictionary(lang)` is a `Record<Lang, () => Promise<...>>` of dynamic `import()`s, so the
unused locale stays out of the server bundle. Unknown input falls back to `DEFAULT_LANG`.

Namespaces: `meta`, `nav`, `home`, `shop`, `product`, `cart`, `cartMenu`, `legal`,
`process`, `roast`, `species`, `contact`, `common`.

**`process`, `roast` and `species` are keyed by Prisma enum values** (`WASHED`,
`MEDIUM_DARK`, `ARABICA`, …) so an enum maps straight to a label. Adding an enum value to
`schema.prisma` therefore requires adding the key to both dictionary files.

## Delivering strings to components

Server pages `await getDictionary(lang)` and pass `dict` (and `lang`) down as props,
including into client components. There is deliberately no translation hook, no context, and
no `t()` function — with two locales and a small surface, prop drilling is cheaper than the
machinery.

## Database content — `pickLocalized`

UI chrome comes from dictionaries; **product content comes from the database**, where
Indonesian columns are required and English ones are nullable
(`name`/`nameEn`, `shortDesc`/`shortDescEn`, `description`/`descriptionEn`, `label`/`labelEn`,
`alt`/`altEn`, `note`/`noteEn`).

```ts
pickLocalized(lang, base, translated?)
```

Returns `translated` only when `lang === 'en'` **and** it is non-blank; otherwise the
Indonesian base. This is what lets English translations be filled in one product at a time
without ever rendering an empty field.

## Adding content

- **New UI string** → add to `id.ts`, then `en.ts` (the type will demand it).
- **New page copy (long-form)** → not the dictionaries. Legal and info bodies go in
  `src/data/legal.ts` as `Record<Lang, LegalDoc>`; page-specific prose lives as a local
  const in the page file.
- **New product** → seed or insert; leave `*En` columns null until a translation exists.
- **New enum value** → `schema.prisma`, migration, then the matching dictionary key in both
  files.
